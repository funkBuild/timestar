**Twelfth pass: allocate filtered results for survivors and amortize block appends — 11 September 2026**

Filtered timestamp decoding now allocates for surviving points, and TSM callers size value buffers after timestamp filtering. Selecting 128 timestamps from a million-point regular stream reduces fresh timestamp capacity from **10 MiB to 1 KiB**, with essentially unchanged decode time. Appending 256 independent 3,000-point blocks reduces vector growths from **256 to 14** and is **4.3× faster** in the isolated benchmark. Default-block HTTP latency is broadly unchanged; several smaller filtered cases remain slightly slower.

The baseline is the completed [eleventh pass](query_pass11_20260911.md). The [production patch](query_pass12_20260911/production.patch) isolates this pass's changes to the timestamp decoder and TSM callers. Preserved baseline sources, server and static library are under ignored `build/perf-query-pass12-before`. [Artifact hashes](query_pass12_20260911/results/artifacts.json) identify both measured builds and drivers. No storage format or public API changes are made.

**Allocation and decoding changes**

Full timestamp reads reserve the bounded requested count for fresh output, removing the previous 25% spare allocation. When multiple streams append to one vector, insufficient capacity grows by approximately 1.5×, or enough for the current append if larger. This amortizes repeated copies. It can retain more spare capacity than the old fixed per-block slack at intermediate sizes.

Filtered reads wait until there are surviving timestamps to append. When allocation is necessary, a helper inspects consecutive following zero-delta headers to count their surviving points. It stops at a nonconstant, invalid, truncated or potentially wrapping group. It neither advances the slice nor raises errors for future headers; the normal decoder remains responsible for validation and early termination. A regression test confirms that a following invalid header beyond the upper time bound remains unconsumed and unvalidated. Existing unsigned wraparound, decreasing sequence, inverted-bound and truncated-count tests continue to pass.

Ordinary filtered groups compact accepted timestamps into the existing 1,024-entry decode buffer, then append once per group. The compacted write position never overtakes unread deltas, and unrolled groups load their deltas before writing. This removes per-survivor vector capacity checks without adding another scratch buffer. Regular groups continue to write arithmetic progressions directly.

TSM aggregation scratch vectors no longer reserve the original timestamp count before filtering. Direct and single-block readers initially reserve full result buffers only for unfiltered reads, and reserve value capacity using the actual surviving timestamp count. Reused buffers retain their capacity; this change does not shrink them. Integer value decoding still materializes full raw integer scratch, and string decoding still performs its existing decompression work.

The full release suite passes **3,943 tests**, with ten existing skips (3,953 total). The focused release selection passes 64 tests. The focused four-shard ASan/UBSan selection passes **77 correctness tests**, including synchronous and file-backed TSM corruption cases. **Measurement method**

GCC 14 release builds run on the Ryzen 9 7950X. Every final CPU comparison uses seven process pairs pinned to CPU 12, alternating after/before and before/after. Each case has one warmup and six measured repetitions. Tables show medians of process medians and median paired speedups. Project builds, tests and other project benchmarks do not overlap performance runs. Standalone drivers exercise the compiled decoder/TSM code with the process allocator, outside a Seastar reactor; allocator-sensitive speedups must be checked against server workloads.

The unchanged primary codec driver covers 60 cases: 1,024 and 65,537 timestamps; regular, three jitter widths and exceptions; aligned and offset-three slices; full, middle and early filters. Both sides reuse preallocated output. Compaction improves irregular middle filtering by roughly 2.5–3%; full decoding remains approximately unchanged.

**Appending independently encoded blocks**

The append driver concatenates 1, 4, 16, 64 and 256 independently encoded blocks into initially empty output. It measures decoding and vector allocation, checks counts inside the loop and compares every concatenated timestamp after timing. Capacity changes are recorded separately from timing.

| Case | Before, µs | After, µs | Paired speedup |
|---|---:|---:|---:|
| points=128 blocks=256 | 1661.781 | 105.650 | 15.729× |
| points=3000 blocks=1 | 0.772 | 0.771 | 1.001× |
| points=3000 blocks=4 | 4.869 | 4.799 | 1.016× |
| points=3000 blocks=16 | 296.433 | 240.272 | 1.239× |
| points=3000 blocks=64 | 1900.994 | 103.346 | 18.531× |
| points=3000 blocks=256 | 17405.387 | 4089.053 | 4.257× |

For both block sizes, 256 appends require 14 growths instead of 256. At 3,000 points per block, final capacity is **6,150,000 → 6,227,712 bytes**. At 16 blocks, capacity rises **390,000 → 546,744 bytes**; this is the spare-memory tradeoff of geometric growth. Allocation behavior changes with buffer sizes and process allocator state: the 64-block case is faster than the 16-block case in the candidate. The results do not establish smooth scaling or a universal server speedup. [All ten append cases](query_pass12_20260911/results/append/summary.json) and [capacity/growth samples](query_pass12_20260911/results/append/memory.json) retain every pair.

**Direct TSM decoding and result memory**

A separate driver constructs valid TSM blocks for all four types at 3,000 and 65,536 points, decodes full/middle/late-128/empty ranges into fresh results, and checks every timestamp/value pair outside timing. It measures encoded-memory decoding without file I/O. Large-block float middle and late reads benefit strongly from smaller allocations, while default-sized blocks and the other value decoders have smaller or mixed CPU changes.

|---|---:|---:|---:|

| type=float n=65536 filter=late | 10.617 | 1.901 | 5.590× |

The larger integer late read is about 4% slower; full integer scratch reconstruction remains. The default-sized boolean middle read is about 6% slower. No uniform improvement across value types is claimed. [All 32 TSM cases](query_pass12_20260911/results/tsm/summary.json) include full and empty controls.

All four empty results have zero timestamp and value-vector capacity after the change. Boolean storage uses capacity bits rounded to bytes. String capacity counts `std::string` objects; the fixture uses short numeric strings, and the figures do not measure arbitrary string payload allocations, decompression buffers or raw integer scratch. Full TSM result capacities remain unchanged.

Whole-process peak RSS is recorded by `/usr/bin/time` for every CPU run. Median peaks are **13,420 → 13,220 KiB** for the primary codec driver, **36,408 → 36,460 KiB** for progression, **29,156 → 25,868 KiB** for appends, and **20,000 → 19,852 KiB** for direct TSM decoding. These include fixtures, runtime state and all cases. The full-read cases dominate some process peaks, so narrower result capacities do not imply corresponding reductions in server peak RSS. Each result directory contains all RSS samples in `memory.json`.

**HTTP controls**

Seven paired server runs use CPUs 8–11 and client CPU 14. Each run loads two 65,536-point regular/jittered series, flushes and restarts before querying, asserts TSM files exist and query-phase WAL files are empty, and independently verifies all responses. Default 3,000-point TSM blocks and `always` WAL durability remain enabled. Each case uses eight sequential connections, each with five warmups and twenty timed requests. Fresh tmpfs directories make this a warm-cache CPU/memory workload rather than a physical-disk test.

Use new output directories and run performance comparisons separately from builds/tests. Baseline measurements require the preserved pass-11 library, not a rebuild of current sources. HTTP drivers own port 18086 for their private server and stop it afterward.

The broader optimization goal remains active. Remaining work includes full integer scratch on selective reads, exact per-append reserves in boolean/string value decoders, spare capacity during multi-block accumulation, first/sparse-exception timestamp groups, sustained compaction and server peak memory. The earlier correction/backfill tradeoffs, high-offset statistics accuracy limitation and unexplained allocator crash are not resolved by this pass.
