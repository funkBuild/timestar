**Fifth pass: skip timestamp scans inside dense buckets — 11 September 2026**

Follow-up: the [sixth pass](insert_pass6_20260911.md) investigates shared timestamp encoding on insert. Its WAL optimization remains provisional pending an allocator-crash investigation.

This pass builds on the completed [fourth pass](query_pass4_20260911.md). The existing million-point bucketed AVG benchmark improved **2.14×**, and timestamp-only COUNT improved **3.08×**. On a separate in-memory HTTP fixture, bucketed queries measured **18–31% lower latency**. Sparse buckets showed smaller, mixed changes, including CPU regressions up to 3.4%.

Production changes are confined to [`BlockAggregator`](../lib/query/block_aggregator.hpp). Previously, `foldSortedMultiBucket` and `addTimestampsOnly` read every timestamp to find consecutive points sharing a bucket. The numeric path then traversed the corresponding values again to aggregate them. A shared `bucketRunEnd` helper now probes ahead, grows the search distance exponentially, and binary-searches the final bracket. Short runs retain a linear scan. For a run of P points, boundary discovery takes O(log P) probes instead of P comparisons; numeric aggregation still processes its values.

The helper uses the existing sorted-input requirement and returns the same bucket boundaries. It also handles the final `uint64_t` bucket without overflowing the end boundary. Ordinary buckets retain their existing SIMD batches and numerical reduction order. At the extreme timestamp boundary, the previous overflow forced one-point runs; the complete final run can now use the existing SIMD fold, with its normal floating-point rounding behavior. No public API or query syntax changes are required.

A [production patch relative to the fourth-pass snapshot](query_pass5_20260911/production.patch) makes this change independently reviewable.

**Existing benchmarks**

The baseline server, performance binary, library and relevant headers were preserved before edits. Both versions use GCC 14 release flags and the same Ryzen 9 7950X. Versions run sequentially in alternating order: after/before, before/after, after/before. Builds and tests do not overlap measurements. The machine is shared; these are local workload measurements.

`QueryFoldBench.*` runs on CPU 4 with one Seastar shard and 4 GiB. The existing harness reports its best of seven repetitions; the following values are medians across three process runs. Q1 and Q5 contain one million points at one-second spacing and five-minute buckets, approximately 300 points per bucket.

| Existing CPU benchmark | Fourth pass | Fifth pass | Speedup |
|---|---:|---:|---:|
| Q1: bucketed AVG through `addPointsRange` | 0.371 ms | 0.173 ms | **2.14×** |
| Q5: bucketed timestamp-only COUNT | 0.265 ms | 0.086 ms | **3.08×** |
| Q2: scalar AVG control | 4.272 ms | 4.278 ms | Unchanged |
| Q4: unbucketed STDDEV control | 0.155 ms | 0.154 ms | Unchanged |

Q1 run timings were 0.368 / 0.371 / 0.380 ms before and 0.177 / 0.173 / 0.172 ms after. Q5 was 0.264 / 0.273 / 0.265 ms before and 0.086 / 0.150 / 0.083 ms after. Q3 SIMD kernel controls are included in the raw logs. Q1 checksums and Q5 counts matched across versions.

**HTTP measurements**

The HTTP fixture contains one numeric series with 262,144 points at one-second spacing. It occupies about 4 MiB of timestamp/value arrays. The probe asserts that no TSM files exist before or after the queries, so the measured data stays in memory; shutdown may subsequently flush it. The server uses four shards on CPUs 0–3, 8 GiB, and default WAL durability. A Python HTTP client uses eight connections per query per run, each with five warmups and ten timed requests. Connection setup, fixture generation, response parsing and hashing are outside request timing. The client is not pinned to a CPU.

Values below are pooled medians of 240 timed requests per query per version across three alternating process runs. Intervals are seconds; the 300-second cases return 874 points and the 4,096-second cases return 65 points.

| HTTP workload | Before | After | Lower latency |
|---|---:|---:|---:|
| AVG, 300-second buckets | 0.246 ms | 0.201 ms | **18.4%** |
| AVG, 4,096-second buckets | 0.163 ms | 0.118 ms | **27.6%** |
| COUNT, 300-second buckets | 0.240 ms | 0.193 ms | **19.6%** |
| COUNT, 4,096-second buckets | 0.172 ms | 0.119 ms | **30.9%** |
| STDDEV, 300-second buckets | 0.283 ms | 0.232 ms | **18.1%** |
| Unbucketed AVG control, 262,144 output points | 9.318 ms | 9.426 ms | 1.2% higher latency |

Every HTTP response passed its expected point-count assertion. Canonical SHA-256 hashes of the first result series for each query/run match across all six server runs. This pass changes neither the native benchmark client nor serialization. The HTTP probe is separate from the native suite used in earlier passes; these timings must not be compared directly with that suite's million-point responses or generalized to disk-bound queries.

**Bucket-size sweep and tradeoffs**

A focused CPU driver tests 262,144 points with 1, 3, 8, 9, 16, 32, 300, 4,096, and 262,144 points per bucket. Both binaries use the same driver against their matching header/library. Each process performs one warmup and six timed repetitions per case, with bucket allocation included and result checking outside timing. Every bucket's count and the exact overall AVG sum are checked.

The final 300-point cases improved 2.02× for AVG and 3.00× for timestamp-only COUNT, corroborating the existing benchmarks. At 4,096 points per bucket, AVG improved 3.38× and timestamp-only COUNT 25.82×: COUNT can skip almost the entire timestamp array in this specialized API. HTTP COUNT still has other work, including examining numeric values in the memory path, so that CPU ratio is not an end-to-end speedup.

Sparse results are mixed. One-point AVG increased from 7.114 to 7.326 ms (3.0%), and three-point timestamp-only COUNT from 1.474 to 1.524 ms (3.4%). Eight- and nine-point cases range from a 3.3% improvement to a 1.4% slowdown. Sixteen- and 32-point cases improve 6–19% in latency. The already-specialized single-bucket controls are unchanged. All cases and individual run values are retained in the [summary](query_pass5_20260911/results/summary.json); small regressions are not excluded from the results.

An initial variant scanned the first eight timestamps before searching. It regressed the nine-point cases by about 12–13%. The retained implementation probes the eighth position first and scans linearly when the boundary is nearby, removing most of that overhead. Initial measurements and their source patch are archived separately under [exploratory](query_pass5_20260911/exploratory/); the tables above use only the final implementation.

**Validation and reproduction**

The final full unit suite passed **3,917 tests**, with ten existing skips and no failures. A four-shard BlockAggregator/query/aggregation selection passed **113 tests**. New tests compare routing with an independent map-based scalar oracle across dense and sparse runs, duplicate timestamps, gaps, nonzero subranges, NaNs and timestamps near `UINT64_MAX`. A separate test checks final-bucket AVG, COUNT, STDDEV, FIRST and LATEST results. [Validation excerpts](query_pass5_20260911/results/validation.txt) and all measurement logs are archived.

Preserved fourth-pass artifacts are under ignored `build/perf-query-pass5-before`. Keep those artifacts before rebuilding for a comparison. The focused driver must compile against the matching `block_aggregator.hpp`, because the optimized methods are inline.
