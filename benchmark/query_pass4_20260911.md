**Fourth pass: aggregation heap and temporary counts — 11 September 2026**

Follow-up: the [fifth pass](query_pass5_20260911.md) improves dense bucket-boundary searches, with CPU and HTTP measurements across bucket sizes.

This pass builds on the completed [third pass](query_pass3_20260911.md). Full-range HTTP AVG decreased from **62.29 to 55.91 ms**, or **1.11× faster / 10.2% lower latency**, using the same corrected benchmark client for both servers. The isolated million-point AVG merge decreased from 20.92 to 19.31 ms, and the benchmark process used about 7.8 MiB less peak memory. Small queries did not show a convincing improvement.

Production changes are confined to `lib/query/aggregator.cpp`. A [patch against the preserved third-pass source](query_pass4_20260911/production.patch) separates this work from the earlier uncommitted changes.

- The N-way merge advances the heap root and repairs it downward once, replacing the previous pop followed by push for streams with remaining input. The heap reserves space for its contributors once. FIRST and LATEST retain the original traversal to preserve equal-timestamp tie selection.
- Compact raw results keep the current timestamp's contributor count in an accumulator instead of retaining a count array for every output point. Values are finalized as each timestamp completes, eliminating a later full-array pass. COUNT avoids unnecessary value summation. An explicit count distinguishes missing NaN inputs from arithmetic NaN, so an indeterminate sum such as `+Inf + -Inf` cannot be overwritten by a later finite contribution.
- Aligned compact results use the constant contributor count directly. They allocate no count array and only require a final value pass for AVG or COUNT. The default API continues returning point counts.

The existing cooperative yield thresholds remain in place. Root replacement can change the order in which equal-timestamp numerical contributions are folded. Floating-point results are therefore not guaranteed to be bitwise identical; cancellation-sensitive sums can differ materially. FIRST/LATEST use the original heap operations, and the regression suite checks other methods against an independent numerical oracle. The numerical-order caveat also matters when considering these measurements for workloads beyond the fixtures below.

**Matched benchmark results**

Measurements use the same Ryzen 9 7950X and GCC 14 release build as the previous pass. Each version runs three times in alternating order: after/before, before/after, after/before. Builds and tests do not overlap the measurements. The machine is shared, so small timing differences remain uncertain.

The existing native HTTP suite runs four server shards on CPUs 0–3 with 8 GiB; the corrected native client runs on CPU 6. Each run uses a fresh data directory, default WAL durability, and the existing protobuf fixture: 100 batches of 10,000 timestamps and ten fields, plus five warmup batches. Values below are medians of three per-run p50s.

| HTTP workload | Third pass | Fourth pass | Latency change |
|---|---:|---:|---:|
| AVG, full range, one million points | 62.29 ms | 55.91 ms | 10.2% lower |
| AVG grouped by host, 1.04 million points | 59.69 ms | 58.12 ms | 2.6% lower; overlapping run ranges |
| LATEST, full range, one million points | 63.10 ms | 62.79 ms | Essentially unchanged |

Full-range AVG run p50s were 62.29 / 61.61 / 63.62 ms before and 58.48 / 55.91 / 55.25 ms after. Grouped AVG was 59.69 / 58.96 / 61.48 ms before and 58.12 / 60.90 / 57.26 ms after. The clearest end-to-end gain is ungrouped AVG. Neither the serializer nor the benchmark client changed in this pass.

All six native suites recorded 515 successful timed requests and 25 expected point-limit failures. Two all-fields cases exceed the ten-million-point pre-merge limit because the load includes warmups. Failed and empty-result cases are excluded from speed claims; a zero harness exit status alone is insufficient validation.

CPU benchmarks run on CPU 4 with one Seastar shard and 4 GiB. The focused driver uses the same compact-output fixture against both libraries: 64 interleaved raw series totaling one million distinct timestamps. Setup is outside timing, with one warmup and six timed repetitions per process. The existing `AggregationStallBench.S2_IncidentPipeline_TwoShards` fixture exercises 195 series × 18,000 points and the count-bearing API. Despite its fixture name, this benchmark invocation runs on one reactor. Table values are medians across three processes; focused timings use each process's median.

| CPU workload | Before | After | Change |
|---|---:|---:|---:|
| Compact AVG merge and response arrays | 20.923 ms | 19.314 ms | 7.7% lower latency |
| Compact STDDEV merge and response arrays | 28.062 ms | 27.425 ms | 2.3% lower; overlapping run ranges |
| Existing 3.51-million-point AVG merge | 152.62 ms | 145.79 ms | 4.5% lower latency |
| Existing 3.51-million-point STDDEV merge | 128.24 ms | 121.95 ms | 4.9% lower latency |
| Focused benchmark process peak RSS | 99.68 MiB | 91.87 MiB | 7.8% lower |
| Unchanged JSON formatting control | 20.458 ms | 21.510 ms | 5.1% higher latency |

RSS is the median process maximum from `/usr/bin/time -v`, not full-server memory. Removing one million `size_t` counts saves an 8,000,000-byte allocation on this platform, consistent with the observed process reduction. The distinct-timestamp fixtures have one contributor per output; multi-contributor correctness is established separately. The unchanged JSON control became slower in this combined process, showing that surrounding execution and measurement variation matter. It is not a formatter optimization claim. All six JSON fixtures produced 26,120,187 bytes and the same FNV-1a hash, `17520365743775275332`.

**Small-query investigation**

The original 3,000-series × 16-timestamp probe used one persistent connection per run. Median-of-run medians initially worsened from 0.874 to 1.050 ms for grouping, 0.552 to 0.591 ms for bucketed AVG, and 0.382 to 0.426 ms for wildcard-filtered bucketed AVG. These results are retained in the archive.

A follow-up sampled eight connections per query per run, with five warmups and ten timed requests per connection. Connection setup is outside timing. Across three runs per version, pooled medians of 240 samples were:

| Short query | Before | After |
|---|---:|---:|
| Grouped AVG | 0.948 ms | 0.962 ms |
| Bucketed AVG | 0.604 ms | 0.604 ms |
| Wildcard-filtered bucketed AVG | 0.400 ms | 0.415 ms |

The large grouping slowdown did not reproduce at that magnitude with broader connection sampling. Filtered queries still measured about 4% slower. Coordinator placement and machine variation are possible explanations, but were not isolated; these measurements do not establish either causality or the absence of a small regression. This pass is retained for the clearer large-result gains and reduced allocation. All archived short-query response series match across both versions after normalizing series order.

**Validation and reproduction**

The full unit suite passed **3,915 tests**, with ten existing skips and no failures. A four-shard query/aggregation selection passed **34 tests**. New tests cover uneven and empty streams, shared timestamps, all-NaN timestamps, contributor counts, and eight methods against a map-based oracle using long-double numerical calculations. A separate regression checks arithmetic NaN preservation. Existing compact/default tests cover all twelve methods, including FIRST/LATEST and mixed raw/state layouts. [Validation excerpts](query_pass4_20260911/results/validation.txt), [machine-readable summaries](query_pass4_20260911/results/summary.json), and raw logs are archived.
