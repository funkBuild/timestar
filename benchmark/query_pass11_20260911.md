**Eleventh pass: decode constant-delta runs directly — 11 September 2026**

Regular timestamp blocks now bypass the decoded-delta buffer and generate arithmetic progressions directly in the result vector. In the final seven-pair comparison, full decoding of 65,537 regular timestamps is **4.1× faster**, middle-range filtering is **8.7× faster**, and selecting the final 128 points from a million-point stream is **83.6× faster**. Irregular filtered cases show a small **1–2% overhead**. Peak process memory is essentially unchanged; this pass reduces work and scratch-buffer traffic, not retained output capacity.

The baseline is the completed tenth-pass worktree. [The production patch](query_pass11_20260911/production.patch) isolates this pass's changes to `integer_encoder_ffor.cpp`. The preserved server, library and source are under ignored `build/perf-query-pass11-before`.

**Implementation and bounds**

After validating the header, the block decoder identifies blocks with zero bit width, zero base and no exceptions. It returns their count and a zero-delta flag without filling the 1,024-entry scratch array. Blocks with exceptions or a nonzero base still use normal unpacking. The scratch array remains available for those blocks; its allocation has not been removed from the outer decoder.

Full reads append the progression directly into the output vector. The loop uses unsigned repeated addition, preserving modulo-2^64 behavior and allowing GCC to generate vector additions. An initial index-times-step expression generated a multiply in each vector iteration; the final induction loop removes it from the steady loop. [Output-loop assembly](query_pass11_20260911/results/appendProgression.asm) is retained.

Filtered reads first prove that the progression cannot wrap, using checked multiplication and an unsigned addition bound. Whole runs below the lower bound are skipped without visiting each timestamp. Only boundary runs need division to locate the first and last included point, and only surviving values are written. Decreasing or wrapped runs use scalar filtering in the original order: check below-min first, then above-max. This also preserves the existing behavior for inverted bounds. The final wrap check uses checked multiplication instead of a division by block count.

The first raw timestamp and first delta retain their special stream semantics, including all-zero first blocks, one-entry groups and empty groups between them. Requested counts still clamp the final group; inclusive endpoints, appended output prefixes, exception transitions and early termination are preserved. No storage-format or public API change is made, and no persistent field or cache is added.

**Correctness**

New tests construct streams from raw block headers and compare results with a scalar timestamp/filter oracle. They cover unsigned boundary values, positive/zero/decreasing steps, modular wraparound, empty groups, 1,024-point boundaries, truncated requested counts, inverted bounds, unaligned slices, existing output prefixes and zero-bit groups with exceptions. A following regular run checks that state carries correctly across an exception block. Separate all-zero fixtures cover short streams and truncated results.

The final release suite passes **3,936 tests**, with ten existing skips. The focused release selection passes 46 tests before the final loop refinements; the final full suite includes those tests. The final ASan/UBSan selection passes **45 correctness tests** on four shards. The release-only single-point timing ceiling is excluded from the instrumented selection and remains enabled in the passing full release suite.

The sanitizer server loads two 65,536-point series, shuts down to flush them, restarts, and completes 1,600 TSM query requests with independently verified timestamps and values. Thirty compatibility streams roundtrip in both baseline and candidate, and their concatenated encoded bytes are exactly equal. [Validation record](query_pass11_20260911/results/validation.txt) and [artifact hashes](query_pass11_20260911/results/artifacts.json) identify the final results and builds. Leak detection is disabled; ASan warns about incomplete makecontext/swapcontext support, and the sanitizer build uses the default allocator rather than the release allocator.

**Memory measurements and remaining allocation work**

Encoded sizes and output capacities match in every corresponding measured case. No retained-capacity reduction is claimed. `/usr/bin/time` records maximum RSS for each complete benchmark process: median peak RSS is **13,300 → 13,268 KiB** for the primary driver and **36,616 → 36,604 KiB** for the supplemental driver. These small changes lie within the observed process ranges. They include fixtures, runtime/library state and all cases in the driver, not isolated decoder or HTTP-server peak memory. [Primary memory data](query_pass11_20260911/results/cpu/memory.json) and [supplemental memory data](query_pass11_20260911/results/progression/memory.json) retain all samples.

The fresh-output fixture confirms a remaining allocation problem: the million-point empty-result query reserves **10,485,760 bytes (10 MiB)** on both sides, despite returning no timestamps. The decoder's existing up-front reservation uses the caller's count bound before filtering. The new path avoids writing those unused result entries, but does not fix this reservation policy. This is a concrete next memory-optimization target.

**TSM HTTP measurements**

The HTTP fixture writes 65,536 regular and 65,536 jittered points, then shuts down cleanly. It asserts that all WAL files were removed and TSM files exist before restarting. Query-phase WAL files must remain empty. The fixture uses default storage settings, including 3,000-point TSM blocks, default `always` WAL durability and fresh tmpfs directories. Each query uses eight connections with five warmups and twenty timed requests per connection. Every response is checked against independent bucket/range calculations.

An initial three-pair run on server CPUs 0–3/client CPU 6 showed improvements for regular queries but substantially slower jittered queries. Because that movement was much larger than the isolated decoder overhead, it was retained and followed by seven pairs on server CPUs **8–11** and client CPU **14**, away from the previously observed busy CPU group. No unrelated process or host setting was changed. The final comparison gives:

| TSM query | Before, ms | After, ms |
|---|---:|---:|
| regular_avg_full | 0.2731 | 0.2536 |
| regular_sum_middle | 0.1581 | 0.1509 |
| regular_avg_early | 0.1366 | 0.1454 |
| regular_count_full | 0.0892 | 0.0922 |
| jitter_avg_full | 0.3563 | 0.3551 |
| jitter_sum_middle | 0.1907 | 0.1894 |
| jitter_avg_early | 0.1405 | 0.1446 |
| jitter_count_full | 0.0875 | 0.0877 |

Regular bucketed AVG is about **7.2% lower latency**, and regular middle-range SUM about **4.6% lower**. Jittered AVG/SUM are approximately unchanged in the final comparison. Early-range and COUNT controls remain mixed, including a 6.4% slowdown for the regular early range. This does not establish a universal HTTP gain or explain every control movement. These are warm-cache CPU/memory measurements, not physical-disk latency estimates.
