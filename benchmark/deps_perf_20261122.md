# Dependency upgrade and read/query/write optimizations — 22 Nov 2026

Branch `release/1.5.0-rc.1`. Everything described here is in the working tree, uncommitted, on top of the
earlier three passes (`benchmark/perf_passes_20261122.md`). Raw results and the drivers that produced them
are in `benchmark/deps_perf_20261122/`.

| Dependency | Was | Now |

| Glaze | 7.2.1 | 9.1.0 |
| Google Highway | 1.2.0 | 1.4.0 |
| CRoaring | 4.1.7 | 5.5.5 |
| Zstd | 1.5.6 | 1.5.7 |
| robin-map | 1.3.0 | 1.4.1 |
| Google Benchmark | 1.8.3 | 1.10.0 |
| GoogleTest | 1.15.2 | 1.18.0 |
| Compiler | GCC 14 | **GCC 15 required** |
| Docker / CI base image | Ubuntu 24.04 | Ubuntu 26.04 |

### What it took

- **GCC 15.** Seastar master uses `std::vector::assign_range` (libstdc++ 15) since 22 Oct 2026; upstream
  supports the two newest GCC majors. The build now prefers `g++-15` and rejects older GCC at configure time
  with an explicit message, instead of a template error inside Seastar. The GCC 13 / C++20 fallback is gone.
  Dockerfiles and CI moved to Ubuntu 26.04, whose default toolchain is GCC 15, with the runtime package list
  updated to match (verified with `ldd` inside the built image).
- **Seastar API changes:** `http::experimental::client` → `http::client`; `seastar::defer` now requires a
  `noexcept` callable (9 sites — behaviour is unchanged: a throwing deferred action already terminated);
  `smp::count` is deprecated in favour of `this_smp_shard_count()`, which must not be called off a reactor
  thread, so a small helper (`lib/utils/shard_count.hpp`) keeps the old "0 when there is no reactor"
  behaviour; `reply::done()` / `set_mime_type()` / the request's `query_parameters` map / the Prometheus
  `metric_help` field are deprecated and no longer used; LTTng tracepoints are on by default upstream and are
  switched off here so the build needs no new system package.
- **Request bodies.** `request::content` is deprecated upstream. Handlers now read the body themselves from
  the content stream through one helper (section 3).
- **Glaze 9** replaced its float printer (Dragonbox) with zmij; the header moved and so did its buffer
  contract, which the response formatter's memory-safety bounds depend on. Re-measured and updated (longest
  text 24 characters instead of 25; scratch reach 34 bytes by contract).
- **CRoaring 5** moved its C++ header (`<roaring/roaring.hh>`).
- **Highway 1.4** uses `unsigned __int128` in a header; with the fetched libraries consumed as ordinary
  includes, CI's `-Werror -Wpedantic` build failed in all ten SIMD files. Fetched dependencies are now
  consumed as SYSTEM includes, the same treatment Seastar already had. This was only visible in the CI
  configuration — it is why that configuration was run in the container rather than assumed.
- **GCC 15** needed one missing `<limits>` include.

### Behaviour that changed with the upgrade

1. **Reactor backend.** The old build only had `linux-aio` and `epoll`. The new one has `io_uring` and
   selects it by default when the kernel permits. See section 2.
2. **Number text in JSON responses.** Every value still parses back to exactly the same double (checked over
   8 million values), and nothing changes for magnitudes in `[1e-4, 1e16)`. Outside that range the notation
   differs: `1E16` where the old printer wrote `10000000000000000`, `2.5E-5` where it wrote `0.000025`. Now
   documented in `docs/api-query.md`. A client comparing response *text* for such values would notice; a
   client parsing numbers would not.
3. **Glaze's generic JSON object** now iterates in document order rather than key order. No observable
   effect was found (all suites pass); noted because it is the kind of change that surfaces later.
4. **Inside Docker**, the default seccomp profile blocks `io_uring`, and Seastar falls back to `linux-aio`
   on its own — verified in the built image.

### Dependency upgrade on its own (no other changes), old build → new build

- JSON array ingest: 113.6M → 114.3M pts/s, 4.58 → 4.55 CPU-s. Protobuf ingest: 60.6M → 59.7M pts/s,
  6.67 → 6.95 CPU-s (the +4% is the `io_uring` default on tmpfs; with `linux-aio` selected the new build
  measures 6.70, identical to the old).
- Queries: flat to 14% faster server-side, except merges of interleaved series, which were consistently
  **10% slower** — a compiler effect, fixed in section 4.

## 2. Reactor backend: `io_uring` vs `linux-aio`

Same binary, same workload, only `--reactor-backend` differs. Process CPU includes every thread.

| Workload | Storage | `io_uring` | `linux-aio` |
|---|---|---|---|
| JSON ingest, 150M points | NVMe (ext4) | 19.7M pts/s, **7.8 CPU-s** | 22.9M pts/s, 27.4 CPU-s |
| Protobuf ingest, 60M points | NVMe (ext4) | 16.1M pts/s, **4.1 CPU-s** | 15.5M pts/s, 14.9 CPU-s |
| JSON ingest, 150M points | tmpfs | 117.2M pts/s, 4.50 CPU-s | 116.3M pts/s, 4.50 CPU-s |
| Protobuf ingest, 150M points | tmpfs | 59.8M pts/s, 6.95 CPU-s | 61.0M pts/s, 6.70 CPU-s |

With `linux-aio`, a shard cannot sleep while any disk I/O is in flight, so an I/O-bound server shows all
shards at 100% CPU; the old build on the same disk behaved the same way (12.1 CPU-s for the 60M-point
protobuf run). `io_uring` sleeps until completions arrive. The work done is the same — the difference is polling. On
tmpfs, which cannot do native asynchronous I/O, `io_uring` hands file writes to kernel worker threads, which
costs about 4% CPU on the write-heavy protobuf run.

The NVMe used is shared and 99% full, and its throughput varied by 2–5× between runs (medians above;
individual runs ranged 3.5–19.9M and 12.5–23.2M pts/s for the JSON row). The CPU figures were stable; the
throughput comparison is indicative only. Raising `--idle-poll-time-us` under `io_uring` did not recover
throughput and cost CPU in proportion.

The default is left at Seastar's (`io_uring`). `[seastar] reactor_backend = "linux-aio"` restores the old
behaviour.

## 3. Request bodies are streamed

Seastar's buffered mode reads the whole body before calling the handler: network chunks are collected, then
copied into one contiguous string, so both copies are live at the peak, and any body up to the server-wide
limit (64 MB, the write limit) is buffered even for an endpoint whose own limit is 1 MB. Handlers now read the
content stream through `timestar::http::readRequestBody` (`lib/http/request_body.hpp`), which refuses an
oversized body from its declared length before reading any of it, and fills a single allocation sized from
`Content-Length`.

Checked against a live server: a 3 MB body to `/query` is answered `413` without being read; chunked uploads
work; a body cut short is answered `400` and nothing from it is written (the peer is gone, but a truncated
protobuf batch can still parse, so partial bytes must never reach a handler); keep-alive connections are
reused. Ingest throughput is unchanged (the copy count is the same; what changes is peak memory and when the
limit applies). Unit-tested in `test/unit/http/request_body_test.cpp` against a scripted stream.

## 4. N-way merge: out of the coroutine frame

After the upgrade, merges of series that take turns (no runs) were 10% slower in the server and 22–40%
slower in isolation. Compiling only `aggregator.cpp` with each compiler and linking everything else
identically reproduced it exactly, and a line profile showed the heap-repair loop alone running ~3× slower:
the heap lived in the coroutine's frame, and GCC 15 re-read the container's bounds from the frame on every
level of every sift.

Hoisting the bounds fixed one path and, tellingly, a variant that helped GCC 15 made the same source 60%
slower under GCC 14 — the loop's speed depended on frame-layout luck. The fix is structural: the
point-by-point loop now runs in a plain function (`heapMergeChunk`) over a heap and accumulator held in
locals, a chunk of input at a time, and the coroutine only yields between chunks. The heap is a fixed array
driven by the same `std::push_heap`/`std::pop_heap` calls `std::priority_queue` made, so the order equal
timestamps come out in — which `latest`/`first` depend on — is unchanged.

Median ms, 10 streams × 100k points (`results/merge_kernel.txt`); all outputs identical:

| Layout, method | Original, GCC 14 | Original, GCC 15 | Final, GCC 15 |
|---|---|---|---|
| interleaved, avg | 6.79 | 8.63 | **5.26** |
| interleaved, latest | 9.02 | 11.09 | 9.42 |
| interleaved, stddev (states) | 26.28 | 25.59 | **22.95** |
| half-aligned, avg | 5.70 | 8.10 | **4.68** |
| half-aligned, latest | 7.76 | 10.53 | 8.58 |
| half-aligned, stddev (states) | 20.20 | 19.39 | **16.20** |
| runs of 2, avg | 6.30 | 7.24 | **4.88** |
| blocky (long runs), avg | 7.58 | 7.45 | 7.41 |

`latest`/`first` on non-run data remain 4–11% behind the GCC 14 build of the old code (they go through the
library's pop/push, which GCC 15 compiles less well), while being 15–19% ahead of what GCC 15 made of it.
Closing that gap would mean hand-writing the heap operations and re-proving the tie order; not done.

Server-level, the interleaved queries went from 10% slower than the old build to 12–15% faster.

## 5. Large JSON query results are streamed

Profile of a 1M-point raw query (30 MB of JSON): the query itself was ~10% of the CPU. Formatting floats was
~32%, **copying the finished body into the connection ~22%**, sending ~13%, formatting integers ~6%. Seastar
copies a string body once more on its way out, so the body existed twice at the peak.

`ResponseFormatter::streamBody` writes the same bytes into ~512 KB segments and hands each to the connection
as a buffer as it fills (chunked transfer encoding), so the body is never held or copied whole and a slow
reader holds the formatter back instead of growing a buffer. It applies to successful JSON results of at
least `http.stream_response_min_points` (default 65,536) for HTTP/1.1 clients; smaller results, HTTP/1.0
clients, errors and protobuf keep `Content-Length`. `0` disables it.

Same binary, streaming on vs off (`results/stream_vs_buffered.txt`):

| Query (points) | Time to first byte | Total | Server CPU / query | Peak RSS |
|---|---|---|---|---|
| avg blocky (1M) | 32.3 → **5.6 ms** | 39.8 → 35.5 ms | 48.0 → 43.8 ms | 250 → 204 MB |
| avg interleaved (1M) | 36.1 → **9.1 ms** | 43.9 → 39.0 ms | 50.9 → 46.6 ms | 250 → 204 MB |
| stddev blocky (1M) | 17.3 → 9.1 ms | 23.1 → 23.0 ms | 31.3 → 31.1 ms | 233 → 204 MB |
| avg aligned (100k) | 5.9 → 3.9 ms | 6.8 → 6.8 ms | 13.3 → 13.3 ms | 196 → 190 MB |

With eight clients each reading a 30 MB result at 1 MB/s, server RSS rose by 322 MB streamed and 552 MB
buffered. Forty clients aborting mid-body and the slow readers left no errors in the log.

The CPU saving (8–9%) is smaller than the copy it removes because Seastar's chunked stream forwards the body
in 32 KB pieces, one send each; the send path went from ~15% to ~24% of the profile. That size is fixed
inside Seastar.

Verified byte-identical to the buffered output over HTTP for six queries and in
`test/unit/http/response_formatter_stream_test.cpp` (every value type, slice and segment boundaries, strings
larger than a segment).

**This is a visible change**: large JSON responses no longer carry `Content-Length`. Any HTTP/1.1 client
handles chunked responses (curl, Node, Python and the Seastar client were exercised), and once the status
line is sent a mid-body failure can only end the connection. Documented in `docs/api-query.md`.

## 6. Per-point JSON batches skip the JSON document

The documented batch format — one object per point — cost **1.2 µs of server CPU per point** against 0.03 µs
for the columnar array format: 40×. About 75% of that was building and freeing a generic JSON document (every
key, string and number a heap node; 10–15× the body in memory).

`scanPlainWriteBatch` (`lib/http/plain_write_batch.hpp`) reads the plain shape — `measurement`, optional
string `tags`, scalar `fields`, optional integer `timestamp` — in one pass into three flat arrays of views
over the body: 85 ns per write against 925 ns for the document parse. It is deliberately not a JSON parser.
It accepts one strict subset and answers "not plain" for everything else, in which case the whole request
takes the existing path, which stays the definition of what a write body means.

The risk in a second reader is that it quietly disagrees with the first, so the subset was drawn by test
rather than by reading: `test/unit/http/plain_write_batch_test.cpp` pushes randomized batches, over 80
hand-written "spoiler" shapes and 6,000 mutated bodies through both paths and requires identical coalesced
output (series, types, exact value bits, timestamps, rejected-entry counts) whenever the scanner accepts.
It found real disagreements immediately — the document reader stores `1e5` as the *integer* 100000 and `1e-1`
as a double, so numbers with an exponent but no decimal point are now left to it — along with the cases
drawn conservatively up front: string escapes and non-ASCII text, integers beyond int64, `-0`, repeated keys,
values that overflow or underflow.

Pre-upgrade build → final build, 4.1M points in 10,000-point requests (`results/ins_final_jb.txt`):

| | Before | After |
|---|---|---|
| Server CPU | 4.49 CPU-s | **1.36 CPU-s** |
| Throughput (bench client is the limit) | 2.96M pts/s | 5.22M pts/s |
| Peak RSS | 392 MB | 281 MB |
| TSM bytes | 8,815,252 | 8,815,252 |

## 7. Bucketed merges across shards: a sorted index instead of a hash map

A bucketed query with fine buckets was the most expensive thing found: `avg` with 1-minute buckets over 1M
minutely points (1M buckets) took **235–250 ms** server-side, against 5 ms for the raw query over the same
points. Over 60% of it was `std::unordered_map`, and ~70% of the wall time was on the coordinating shard,
which moved every node of every shard's map into one map (an insert each, with rehashes as it grew), pulled
every node back out, and sorted the points.

When the shards' partials carry mostly *different* buckets, the coordinator now indexes the states where they
are — a flat array of (bucket, state) per partial — puts it in bucket order (a map filled in time order
iterates newest-first, which is a reversal; otherwise chunked sorts and stable merges, yielding between
steps), and folds runs of equal buckets in one pass, emitting the points already ordered. No hash operations
and no final sort. There is at most one partial per shard at this point, so the index is 16 bytes per bucket
per shard on top of the states themselves.

When the partials carry the *same* buckets (many series, coarse buckets — the usual dashboard query) the old
map fold is just lookups that hit, and it measured 5–15% faster than the index for some methods; a single
partial needs no merge at all. So the route is chosen from a 256-bucket sample of how much two partials
overlap. All three routes fold a shared bucket in the same order as before — the first partial's state
absorbs the others in partial order — which `BucketedPartialsMatchLeftFoldOracleOnEveryRoute` checks
bit-for-bit for twelve methods and eight overlap shapes.

Pre-upgrade build → final build, 114 bucketed queries (`results/bucketed_merge.txt`):

| Query | Buckets | Before | After |
|---|---|---|---|
| avg / min / max / sum / count / latest / first, 1m buckets, disjoint across shards | 1,000,000 | 219–235 ms | **132–134 ms** (1.64–1.76×) |
| stddev / stdvar / spread, same | 1,000,000 | 223 ms | 134–136 ms (1.65×) |
| median, same | 1,000,000 | 196 ms | 109 ms (1.80×) |
| max by rack, 1m buckets | 1,000,000 | 183 ms | 111 ms (1.65×) |
| avg by host, 1m buckets (one partial per group) | 1,000,000 | 75 ms | 75 ms |
| shared buckets, 1m (aligned / interleaved layouts) | 100,000 | 54–57 ms | 53–56 ms |

Across all 114: median 1.06×, none slower beyond noise (one at 0.94×, 25.2 → 26.9 ms). Results are identical
to the baseline's. One thing this surfaced that is **not new**: a handful of float aggregates (sums,
variances) differ in their last digits from run to run *within either build*, because shard partials are
merged in arrival order.

What remains is the rest of the same problem: 133 ms is still 25× the raw query. Each bucket state is still
hash-inserted on the shard (once per series, once into the shard's group), still shipped as one heap node
per bucket, and still freed on a shard that did not allocate it. Carrying bucketed partials as sorted flat
vectors end to end would remove all three; it touches the block aggregator, the per-shard group merge and
~70 test sites, and the per-shard merge cannot simply reuse this index (there the number of partials is the
number of series, so an index over all of them costs memory proportional to series × buckets).

## Found and measured, not changed

- **The rest of bucketed aggregation** (section 7): the per-shard, per-series bucket maps and their node-by-node
  transport. Still the largest known query-path cost.
- **Response send path.** 32 KB chunks, one send each, under chunked encoding (section 5); fixed in Seastar.
- **Float formatting** is ~32% of a large JSON response and already uses the fastest known algorithm;
  integer (timestamp) formatting is ~6%. A SIMD integer formatter could halve the latter.
- **`latest`/`first` merges on non-run data**: 4–11% behind the GCC 14 build (section 4).
- **Plain-batch scanner**: now ~7% string scanning and ~6% number parsing of a path that is no longer
  server-bound.
- Carried over from the earlier report, unchanged: memory-store pre-sizing from the retiring store (−9%
  ingest CPU for extra transient memory per shard), and a size-aware ALP parameter search.

## Things to know

- **`WALTSMRolloverTest` (integration suite) was failing before this work**: three tests assumed the 16 MB
  WAL threshold that became 64 MB in July (`efa64e5`) and wrote only ~14 MB. They now pin their own 4 MB
  threshold. CI does not run the integration suite, which is how it went unnoticed.
- **CI's benchmark job builds a target that does not exist** (`bool_encoder_benchmark`, removed with the
  legacy encoders; `benchmark/run_ci_benchmarks.sh` also runs it). Not introduced here and not fixed.
- The reformatting script used for one mechanical replacement also rewrote six stale object files under
  `lib/CMakeFiles/libtsdb.dir/` — leftovers of an in-source build from August 2025 of a target that no longer
  exists, ignored by git. They were already unusable; mentioned so the changed timestamps are not a mystery.
- Benchmarks ran on a shared machine (load average 7–23 throughout). Each comparison alternates the two
  builds and reports medians; CPU-seconds were far more stable than throughput.
