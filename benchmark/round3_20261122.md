## 1. Bucket states: a map shaped for how aggregation uses it

The previous round replaced the coordinator's hash-map merge and noted what was left: every bucket state was
still a heap node in a `std::unordered_map`, hash-inserted once per series and again into the shard's group,
shipped between shards node by node, and freed on a shard that did not allocate it.

`BucketMap` (`lib/query/bucket_map.hpp`) replaces that map everywhere on the query path. It keeps the parts
of the `unordered_map` contract the code relies on — `operator[]` default-constructs, references stay valid
across insertions — and changes what was costing time:

- Entries live in insertion order in a few large blocks. A series is decoded in time order, so its buckets
  are created in ascending order: insertion order *is* bucket order, the map knows it (`sortedByKey()`), and
  consumers then need neither a hash nor a sort. A million entries is ~250 allocations instead of a million.
- A key greater than every key so far is appended without looking anything up.
- A lookup first tries the entry after the previous hit — which is what folding one time-ordered series into
  another asks for every time — then gallops or bisects from there while the map is in order.
- Only a map whose entries are out of order builds a hash index, lazily.

On top of it:

- **Shard, series → group.** When a series' buckets are ones the group already has, the fold is in place and
  every lookup is "the next entry". When they mostly are not (series active at different times), the two
  ordered maps are merged into a new ordered one rather than paying an out-of-order insert per bucket — only
  when the series is at least an eighth of the group's size, which bounds the moving.
- **Coordinator.** A single partial in bucket order is emitted directly, no sort. Partials that share
  buckets fold in place; partials that mostly do not fold through the sorted index from the previous round,
  whose "sort" is now usually nothing.
- States are released while they are still in cache, and the map's storage is then freed without a second
  pass over a million cold states.

Per bucket, the operations are exactly what they were — the earlier series' or partial's state absorbs the
later ones in order, and a bucket new to a group starts from a default state that absorbs the incoming one
(which is *not* bit-identical to moving the state, so it is preserved). Two tests compare every route
against the plain loop, bit for bit: `FoldingSeriesIntoAGroupMatchesThePlainLoop` and
`BucketedPartialsMatchLeftFoldOracleOnEveryRoute`. The container itself is tested against
`std::unordered_map` under random operations (`bucket_map_test.cpp`).

`results/bucketed_bucketmap.txt` (114 queries: 11 methods × 3 layouts × 3 intervals, plus group-by and
start-aligned variants):

|---|---|---|---|
| 11 methods, 1m buckets, series active at different times | 1,000,000 | 132–136 ms | 41.6–42.9 ms (median alone 55 ms) |

47× two rounds ago.

## 2. Per-timestamp state merge: no state for a lone value

`stddev`, `spread` and `median` without an interval merge per-timestamp states. Most timestamps have exactly
one contributor, and for those a full state was built from the one raw value only to read the answer back
out — a lone finite value is its own avg/min/max/sum/latest/first/median, has count 1 and zero spread and
variance. The merge now carries just the value until a second contributor arrives
(`Aggregator::loneValueResult`; NaN, infinities, -0.0 and the sentinel timestamp go through the state
itself). `LoneValueMatchesAStateOfOne` holds the closed forms to the state for every method.

This was also a regression fix found mid-round. After the bucket-map work, `stddev` with no interval took
20.7 ms to first byte instead of 8.9 — in code that had not been touched: the compiler had stopped optimising
the temporary state away because *other* code in the same file changed.

## 3. Merge kernel: inlining stated, not left to heuristics

The same thing showed in the isolated benchmark: with the lazy state in place, the untouched raw-value paths
moved by ±25% (interleaved avg 5.2 → 7.1 ms). The previous round moved the loop out of the coroutine frame;
what gets inlined into it was still the compiler's choice, and it changed whenever the file did.

The heap operations and the small per-timestamp callbacks are now `always_inline` at their definitions, and
the run path and the state fold are `noinline`. Two builds of the same source compiled differently (as part
of the library, and on its own) now agree to within noise.

## 4. Short decimals are formatted without the general algorithm

Float formatting was about a third of the CPU of a large JSON response. The general algorithm (shortest text
that parses back to the same double) costs 12–15 ns a value, but most metric values are not arbitrary
doubles: they are integers or readings with a few decimal places. If a value is the double nearest to
m / 10⁶ for an integer m below 10¹⁵, that decimal with trailing zeros dropped *is* the shortest text that
round-trips — it has at most 15 significant digits, and no two decimals that short parse to the same double.
`writeShortDecimal` (`lib/http/short_decimal.hpp`) tests that with one multiply, one divide and a compare,
and writes the digits with integer arithmetic. Whole numbers up to 10¹⁵ take the same path. Everything else
— values needing a seventh decimal, magnitudes below 1e-4, zero, non-finite — goes to the general writer as
before, and after eight declines in a row the fast path is left alone for the next 256 values.

The bytes are identical to the general writer's: checked over 241 million values in the benchmark driver and
over 20 million in `ShortDecimalWriterMatchesTheGeneralWriter`.

| Values | General writer | With fast path |
|---|---|---|
| integers | 15.1 ns | 3.8 ns |
| 1–3 decimals | 15.0 ns | 5.3–5.8 ns |
| multiples of 0.25 | 15.0 ns | 8.0 ns |
| 6 decimals | 15.1 ns | 4.8 ns |
| whole numbers 1e9–1e13 | 15.1 ns | 5.1 ns |
| full-precision doubles | 12.1 ns | 12.5 ns (before the back-off) |

End to end, 1M-point responses of two-decimal values (`results/large_json_queries.txt`): total 35.3 → 30.5 ms,
server CPU 43.7 → 38.7 ms per query.

## Checking equality

Digest comparison turned out to be the wrong tool for aggregates: a handful of float results differ in their
last digits from run to run *within one build*, because shard results are merged in arrival order (noted
last round; confirmed here — two runs of the baseline disagreed on 18 of 114 queries by up to 9.5e-16
relative). So the bucketed results were compared numerically across builds (`tools/num_cmp.py`): no
structural differences in any of the 114 queries, 113 bit-identical in the final run, the remaining one
differing by 3.2e-16. The 18 no-interval and coarse-bucket queries of the standing suite matched by digest.

## Looked at and left alone

- **Memory-store vector relocation** is 11–14% of JSON-array ingest CPU (the per-series vectors double as
  they grow, and each doubling copies cold memory). Every fix either commits memory earlier (pre-sizing from
  the retiring store: −9% CPU for roughly +0.6× the WAL threshold per shard at rollover — measured in an
  earlier round, and at odds with the low-memory goal) or rewrites the insert path around adopted chunks with
  lazy consolidation, which touches last-write-wins handling and ~100 test sites. Still your call.
  *(Done afterwards — `benchmark/memstore_runs_20261122.md`.)*
- **ALP on full-precision doubles** (protobuf ingest): the parameter search (~9%) and a scalar scan (~6%)
  are wasted when the block falls back to ALP_RD, but skipping either changes which encoding is chosen in
  near-tie cases, and no cheap bound proves the outcome in advance. Left byte-identical.
- **JSON-array ingest otherwise**: ~22% number parsing, ~17% network and kernel. Near its floor.
- **The default state every new bucket starts from** (~8% of a fine-bucket query): required to keep folds
  bit-identical to what they were.
- Carried over: the 32 KB send granularity inside Seastar's chunked stream; integer (timestamp) formatting
  at ~6% of a large response; CI's benchmark job referencing a target that no longer exists.
