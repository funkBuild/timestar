**Second pass: query execution and aggregation — 11 September 2026**

**Benchmark update:** the [third pass](query_pass3_20260911.md) found and fixed quadratic response copying in the native query client. Its corrected comparisons clarify the large HTTP timings below; CPU benchmarks and Python probes are unaffected.

This pass implements three further query optimizations. Comparisons are against the completed [first pass](performance_optimizations_20260911.md), not the original release. The strongest gains are a 2.49× faster large STDDEV merge and a 1.50× faster short, high-cardinality grouped HTTP query. Large AVG response latency is largely unchanged.

**What changed**

1. **Finalize aggregation state as each timestamp completes.** `nWayHeapMerge` now retains only the current timestamp's accumulator and emits its final value when the heap advances. STDDEV, STDVAR, SPREAD, and median/state merges no longer build an intermediate `vector<AggregationState>` for every output timestamp and then walk it again. The heap order and per-timestamp fold order remain unchanged. Raw/state mixtures, NaNs, counts, and median saturation retain their existing semantics. Raw-value merges use the same merge implementation.
2. **Reduce many short, aligned series on their owning shard.** Before returning shard results, `compactAlignedPartialGroups` reduces eligible groups into one sorted state partial. Eligibility requires at least 16 contributors, each containing at most 256 points, with exactly identical timestamp vectors. The threshold ensures that replacing raw points with larger states still reduces intermediate data size. Other series continue through the existing raw merge. Total input-point counts remain intact for query limits; AVG uses counts and STDDEV uses Welford state across shards. FIRST/LATEST and median methods are excluded from this optimization to retain their existing tie/fold behavior. The first pass's small grouped-query regression motivated this bounded reduction.
3. **Reuse bucket maps and transfer nodes.** Bucket merging adopts the first partial's map and transfers nodes for new buckets. Duplicate buckets merge into existing nodes. This avoids allocating a replacement node for each bucket and avoids reserving the sum of all partial sizes when most shards contain the same buckets. Consumed nodes still release at existing yield points.

Changes are confined to `lib/query/aggregator.{cpp,hpp}` and one call in `lib/http/http_query_handler.cpp`, with regression tests and benchmark artifacts.

**Measurements**

Release build, GCC 14, `-O3 -g -DNDEBUG -march=native`, Ryzen 9 7950X. The machine was shared. The first-pass server and performance-test executables were preserved in `build/perf-query-pass2-before` before editing. Each version ran three times in alternating order: after/before, before/after, after/before. Builds and unit tests did not overlap these measurements.

| Measurement | First pass | Second pass | Change |
|---|---:|---:|---:|
| STDDEV merge, 195 series × 18,000 points | 317.38 ms | 127.47 ms | **2.49× faster** |
| Longest reactor scheduling gap during that merge | 11.59 ms | 0.74 ms | **93.6% lower** |
| Peak RSS of the AVG + STDDEV benchmark process | 725.3 MiB | 323.1 MiB | **55.4% lower** |
| Short grouped AVG, 3,000 series | 1.339 ms | 0.891 ms | **1.50× faster** |
| Bucketed AVG over that dataset | 0.591 ms | 0.571 ms | 3.4% lower latency |
| Wildcard-filtered bucketed AVG | 0.406 ms | 0.385 ms | 5.1% lower latency |
| Large AVG merge in the same CPU benchmark | 159.74 ms | 155.79 ms | Approximately unchanged |

The merge measurements use the **existing** `AggregationStallBench.S2_IncidentPipeline_TwoShards` test, pinned to CPU 4 with one Seastar shard and 4 GiB. It models two shards' partials and merges 3.51 million globally distinct timestamps into one result group. Both methods assert the complete output point count. Numbers are medians of three runs. The reactor gap is the longest delay observed by the existing competing yield-loop probe; it is not a universal maximum-latency guarantee. `/usr/bin/time -v` measures peak resident memory for the whole benchmark process, including both AVG and STDDEV phases; it is not a full HTTP server memory measurement.

STDDEV merge times were 319.11 / 315.73 / 317.38 ms before and 137.48 / 126.90 / 127.47 ms after. Peak RSS ranged 742,000–743,252 KiB before and 330,684–331,208 KiB after. The state vector removal accounts for the substantial reduction in transient storage, while result points and input arrays still occupy memory.

The HTTP high-cardinality probe uses four shards on CPUs 0–3, 8 GiB, and default WAL durability settings. It loads 3,000 series with 16 aligned timestamps each and ten rack groups. Each run records 30 timed requests following five warmups. The table pools 90 samples per query/version. Grouped-query run medians were 1.328 / 1.333 / 1.502 ms before and 0.904 / 0.872 / 0.885 ms after. An initial non-interleaved baseline ranged 1.051–1.580 ms, illustrating machine variability. Every compared response matched exactly after normalizing unspecified series ordering. The single-digit bucketed-query changes are modest and should not be treated as strong standalone claims about node transfer performance.

**Broader HTTP query checks**

The existing native query suite ran against both servers after the same native protobuf fixture load. Each server returned 515 successful timed queries and 25 point-limit failures from the existing two all-fields cases. Failures and empty results are excluded from speed comparisons. The 10.5-million-point fixture includes warmups and intentionally exceeds the configured 10-million-point pre-merge limit for those cases; the harness still exits successfully despite these query failures.

| Native HTTP case | Before median | After median | Output |
|---|---:|---:|---|
| LATEST, full range, one field | 382.77 ms | 381.89 ms | 1,000,000 points |
| AVG, full range, one field | 378.30 ms | 389.54 ms | 1,000,000 points |
| AVG grouped by host, full range | 437.00 ms | 427.30 ms | 1,040,000 points |
| AVG, one-day buckets | 0.43 ms | 0.33 ms | 695 points |

These are one native-suite run per version, with five timed iterations for the AVG cases and 20 for LATEST. The full-range results show no broad speedup: ungrouped AVG was about 3% slower, while grouped AVG was about 2% faster, within the observed run variation. Large responses still contain roughly 38–40 MB of JSON.

**Correctness and remaining costs**

New tests cover short-series compaction across distinct groups, exact timestamp alignment, the size cap, excluded methods, unequal cross-shard AVG weights, all-NaN timestamps, COUNT/SUM/MIN/MAX/SPREAD/STDDEV/STDVAR, and actual HTTP handler execution across owning shards. Existing aggregation tests exercise mixed raw/state partials, disjoint and overlapping timestamps, median behavior, and FIRST/LATEST ties. See [validation.txt](query_pass2_20260911/results/validation.txt) for final test outcomes.

The next sizable candidates are keeping merged results in parallel timestamp/value arrays through HTTP response construction, and reducing the per-series discovery/execution overhead on very wide queries. The current HTTP finalizer still splits `AggregatedPoint` arrays into separate vectors. This pass does not alter that internal result contract or response serialization. Large/misaligned short groups that fail the alignment check retain the general merge; the shard-local reduction is deliberately bounded rather than an attempt to solve every grouping shape.
