**Third pass: query result construction, JSON output, and benchmark accuracy — 11 September 2026**

Follow-up: the [fourth pass](query_pass4_20260911.md) implements the count-storage and heap improvements identified below, with incremental measurements and a small-query regression investigation.

Implemented two more database optimizations and corrected a major cost in the native benchmark client. The baseline is the completed [second pass](query_pass2_20260911.md). With the **same corrected client for both servers**, full-range AVG improved from 69.63 to 61.61 ms and full-range grouped AVG from 68.88 to 58.82 ms. Those are incremental database gains; the reduction from earlier native timings near 400 ms mostly comes from fixing the client itself.

**Implemented changes**

- **Keep unbucketed response data in parallel arrays.** `Aggregator::mergePartialAggregationsGrouped` accepts an optional `compactOutput` flag, enabled by both HTTP finalizers. Raw merges finalize values in their existing arrays. State merges emit final doubles directly beside timestamps. Single-partial COUNT and state-method results also use arrays. This avoids building `AggregatedPoint` objects only to split them into timestamp/value arrays immediately afterward. The default result form retains contributor counts for existing callers. AVG/COUNT still use the correct contribution counts internally, and state-based methods retain their normal accumulators. Bucketed and collapsed results retain their existing paths.
- **Serialize only initialized output bytes.** The JSON formatter reserves capacity but uses C++23 `std::string::resize_and_overwrite` for bounded appends. Previously it zero-filled a worst-case 66 bytes per point before writing the response. The new callbacks return the actual initialized length, so unused capacity never becomes part of the string. Numeric arrays retain their existing 65,536-element yield slices; string escaping, integer formatting, and NaN/Inf-to-null behavior are unchanged.
- **Correct quadratic response copying in `timestar_query_bench`.** The client accumulated received chunks with `seastar::sstring::append`. The local Seastar implementation allocates a new string and copies the entire prefix on every append (`external/seastar/include/seastar/core/sstring.hh`). Replacing the accumulator and final response buffer with `std::string` gives geometric growth. This is a benchmark-client optimization, **not a database speedup**. Both server versions below use that same corrected client.

A [production patch relative to the second-pass source snapshots](query_pass3_20260911/production.patch) makes this pass reviewable independently of the earlier uncommitted changes.

**Corrected HTTP comparisons**

Ryzen 9 7950X; GCC 14 release build with `-O3 -g -DNDEBUG -march=native`. Four server shards on CPUs 0–3, 8 GiB, default WAL durability. Native client on CPU 6 with 2 GiB. Fresh ext4 data directory and the same native protobuf fixture for each run: 100 batches × 10,000 timestamps × ten fields, plus five warmup batches. Server versions alternate after/before, before/after, after/before. Builds/tests do not overlap measurements.

The table reports the median of three per-run p50 values from the existing native query suite:

| HTTP query | Second pass | Third pass | Improvement |
|---|---:|---:|---:|
| LATEST, full range, one field | 71.00 ms | 62.21 ms | 1.14×; 12.4% lower latency |
| AVG, full range, one field | 69.63 ms | 61.61 ms | 1.13×; 11.5% lower latency |
| AVG grouped by host, full range | 68.88 ms | 58.82 ms | 1.17×; 14.6% lower latency |

LATEST returns one million points here; it does not collapse the time range without an interval. Ungrouped AVG also returns one million points; grouped AVG returns ten series and 1,040,000 points. Responses remain roughly 38–40 MB. Each run times 20 iterations for LATEST and five for the two AVG cases, after the native harness's warmups.

Grouped-query run medians were 67.55 / 68.88 / 70.39 ms before and 58.82 / 58.32 / 60.77 ms after. Ungrouped AVG was 69.63 / 69.61 / 75.23 ms before and 60.94 / 61.61 / 63.50 ms after. The machine was shared, so these remain local workload measurements rather than production guarantees.

All six native suites recorded 515 successful timed requests and 25 configured point-limit failures. As in earlier passes, two all-fields cases exceed the ten-million-point pre-merge limit because the fixture includes warmups. Failed and empty-result cases are excluded from speed claims. The harness's successful exit status alone does not establish query success.

**Why earlier native timings were much larger**

Before correcting the client, this pass measured the second-pass server's full AVG at 372.04 ms and grouped AVG at 404.25 ms. With the corrected client, that same server version measures about 70 ms. The old timings included repeated copying of a growing response buffer. They remain observations of that client/server setup, but are unsuitable as estimates of server execution cost. The large reduction caused by the client correction is not included in the database improvement table. Earlier CPU benchmarks and the Python high-cardinality/insert probes do not use this client and are unaffected.

**CPU and memory measurements**

A new focused driver measures the result form the HTTP finalizer needs: timestamp/value arrays. It compiles the same fixture against the preserved second-pass library/headers and the current library. The old path's timing includes splitting point structs; the new path requests arrays directly. There is no network or disk I/O. It runs on CPU 4, one Seastar shard, 4 GiB. Each process performs one warmup and six timed repetitions, and versions are interleaved across three processes each.

| CPU workload | Before | After | Change |
|---|---:|---:|---:|
| AVG merge and response-array construction | 26.373 ms | 20.316 ms | 1.30× faster |
| STDDEV merge and response-array construction | 30.359 ms | 27.141 ms | 1.12× faster |
| JSON formatting | 23.418 ms | 20.524 ms | 1.14× faster |
| Whole benchmark process peak RSS | 145.4 MiB | 99.9 MiB | 31.3% lower |

Numbers are medians of the three process medians; RSS is the median process maximum from `/usr/bin/time -v`. The memory result covers the combined driver, not a full HTTP server or a per-query allocation count.

The merge fixture contains 64 interleaved series totaling one million distinct timestamps. STDDEV therefore has one contributor per output timestamp; multi-contributor correctness is covered by regression tests, not implied by this particular speed measurement. Setup is outside timing, and output count plus sampled values are checked. The serializer fixture contains one million timestamps and short fractional values, producing exactly 26,120,187 bytes. All six processes produced the same full-output FNV-1a hash: `17520365743775275332`. This establishes unchanged bytes for that fixed fixture, alongside the parser-based tests.

**Small-query check and validation**

The Python 3,000-series/16-timestamp probe was repeated three times per version in alternating order. Pooled medians were 0.921 → 0.940 ms for unbucketed grouping, 0.605 → 0.591 ms for bucketed AVG, and 0.414 → 0.415 ms for wildcard-filtered bucketed AVG. These small differences are within the observed spread; this pass primarily benefits large results. An initial single pair varied more and is archived rather than used for a speed claim. Every repeated high-cardinality result matched after normalizing series order.

The full unit suite passed **3,913 tests**, with ten existing skips and no failures. A four-shard query/aggregation/formatter selection passed **43 tests**. New tests compare compact and count-bearing results across all twelve aggregation methods and six layouts: single raw, aligned finite data, aligned NaN data, misaligned data, mixed raw/state, and single-state partials. Serializer tests cover the yield boundary, numeric extrema, underestimated reservation, large escaped strings, bools, exact signed integer limits, empty arrays, and non-finite doubles. See [validation details](query_pass3_20260911/results/validation.txt).

**Remaining opportunities**

The raw merge still maintains a count vector for methods that only need to know whether any non-NaN value exists. Its heap also performs a pop and a push for most input points. Method-specific accumulator storage and a replacement-at-root heap are candidates for a later pass, with careful NaN and FIRST/LATEST tie testing. This pass does not change those algorithms or the protobuf encoder. The native benchmark still needs clearer handling of failed and empty cases before it can serve as an unattended performance gate.

**Reproduction**

[Drivers, raw results, and source patch](query_pass3_20260911/) are archived. The preserved second-pass binaries/library and source snapshots are under ignored `build/perf-query-pass3-before`. Preserve these before rebuilding when reproducing a comparison; both HTTP versions must use the corrected current query client.

```bash
cmake --build build --target timestar_http_server timestar_query_bench timestar_perf_test timestar_unit_test -j 8
python3 benchmark/query_pass3_20260911/compile_cpu_bench.py before
python3 benchmark/query_pass3_20260911/compile_cpu_bench.py after

# Fresh output directories; sequential versions, no concurrent build/test load.
python3 benchmark/query_pass3_20260911/compare.py "$PWD/build/query-pass3-repeat"
python3 benchmark/query_pass3_20260911/compare_http.py "$PWD/build/query-pass3-http-repeat"
```

`compile_cpu_bench.py before` uses the preserved `liblibtimestar.a` and `lib/query/aggregator.hpp`; matching include/link flags come from the release build's compilation database and performance-test link command. The HTTP drivers start private servers on port 18086 and stop them afterward. Corrected native logs, old-client logs, CPU timings, and repeated high-cardinality responses are separately named in [results](query_pass3_20260911/results/).
